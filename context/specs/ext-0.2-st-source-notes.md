# Session Lease — SillyTavern Source Notes

What the session lease spec (`ext-0.2-session-lease-spec.md`) relies on in SillyTavern's source, confirmed per ST version (its E15). Re-check on every ST release (E12).

Checked against the tags **1.19.0 and 1.19.1** (2026-11-20). Between them only `characters.js` (character import), `charx.js`, `users-admin.js`, `users-private.js` and a CSS fix in `public/scripts/chats.js` changed, none of it below.

- **Allowlist (E6):** each handler read. Read-only for user data, with these side effects that never overwrite anything: `characters/all`, `characters/get` fill ST's character cache; `groups/all` and `chats/get` create an empty folder if missing; `secrets/read` creates an empty `secrets.json` only if none exists; tokenizers may download models into the global `_cache`. `stats/get` reads memory. **Excluded:** `backgrounds/all` (`getOrGenerateMetadataBatch` reads `image-metadata.json`, adds metadata and writes the whole index back, folder assignments included)
- **Chat saves (E7):** `POST /api/chats/save`, `POST /api/chats/group/save` (`src/endpoints/chats.js`). `saveChatConditional` sets `isChatSaving` and clears it in `finally`; the group save returns on a failed fetch. ST's `beforeunload` prompts while `isChatSaving` or `this_edit_mes_id >= 0`
- **CSRF (E6):** `src/server-main.js` registers `GET /csrf-token` before `requireLoginMiddleware`; `csrf-sync` 4.2.1 `generateToken(req)` returns the session's token unless `overwrite`; sessions are `cookie-session`. ST's page fetches its token in `firstLoadInit`
- **Lease files:** `/user/files/*` answers 404 for a missing file, 403 when not logged in. `POST /api/files/upload` validates the name and writes with `writeFileSyncAtomic`
- **Login page:** `GET /login` serves `login.html`; it requests `/csrf-token` and `/api/users/list`, `/login`, `/recover-step1`, `/recover-step2` only
- **WebSockets and other channels (R31):** no WebSocket server in `src` (the `ws` dependency isn't imported), no `new WebSocket`, `EventSource`, `sendBeacon`, workers or service worker in `public` outside `public/lib`; streaming uses `EventSourceStream` over fetch bodies; `<form method="post">` elements use `action="javascript:void(null)"`. Memory Books and TopInfoBar on the test install: none either
- **`GET /version`** answers `{ agent, pkgVersion, gitRevision, gitBranch, commitDate, isLatest }` (behind the login check)
- **Generation endpoints (E8):** `src/server-startup.js` mounts `/api/backends/text-completions`, `/api/backends/kobold`, `/api/backends/chat-completions`, `/api/novelai` and `/api/horde` (same lines in 1.19.0 and 1.19.1); each has `POST /generate` (Horde: `/generate-text`). Other `/generate` routes are images, voice or video (`/api/sd/*`, `/api/novelai/generate-image`, `/api/azure/generate` is Azure TTS, `/api/speech/*`) and stay off the list. Every caller in `public/scripts` (`script.js` `sendGenerationRequest`, `openai.js`, `textgen-settings.js`, `kai-settings.js`, `nai-settings.js`, `custom-request.js`, `horde.js`) reads the response body to the end (`json()`, `text()` on errors, or `pipeThrough` of the stream), so `busy: false` follows; Stop aborts the fetch, which errors the stream
- **Reopen (E4)** (2026-11-21; `script.js`, `group-chats.js`, `st-context.js`, `welcome-screen.js` identical in 1.19.0 and 1.19.1): `getContext()` exposes `selectCharacterById`, `openCharacterChat`, `openGroupChat`, `getCurrentChatId`, `characters`, `groups`, `characterId`, `groupId`, `chatId`, `onlineStatus`, `mainApi`, `eventSource`, `eventTypes`; it builds a new object on every call. `selectCharacterById(id)` returns without switching while `isChatSaving` or a reply runs; ST's own recent-chat code (`welcome-screen.js`) passes no options (default `switchMenu: true`), and so does the lease. `openCharacterChat(file)` sets `characters[this_chid].chat` and saves the card (as when the user picks a chat). `openGroupChat(groupId, chatId)` doesn't select the group; ST's own callers (`openRecentGroupChat`, `/go`, auto-load) call `openGroupById` first, which isn't in the context. `globalThis.SillyTavern` is set before `script.js` waits for `load` (line 293; the wait, its only top-level `await`, at line 339), but `getContext()` reads `let`s declared after it (`name1`, `chat`, `characters`, `this_chid`, …), so until `script.js` resumes it throws a `ReferenceError` (temporal dead zone; seen in the app, 2026-11-21). ST's `load` listener is added when `script.js` runs, after the app's document-start lease added its own, so the lease's runs first and sees the error; one task later the module body has run to its end (the retry is unverified in the app until rc.2); `APP_READY` and `APP_INITIALIZED` are auto-fired for late listeners. Events: `APP_READY` `app_ready`, `CHAT_CHANGED` `chat_id_changed`, `ONLINE_STATUS_CHANGED` `online_status_changed` (emitted only when the status changes)
- **Connect buttons (E10)** (2026-11-21; `RossAscends-mods.js`, `index.html` identical in 1.19.0 and 1.19.1): `RA_autoconnect` presses `#api_button` (kobold), `#api_button_novel`, `#api_button_textgenerationwebui`, `#api_button_openai`; no case for `koboldhorde`. All four are `<div>`s with jQuery click handlers, which run even while the button looks disabled. An attempt in progress: each handler calls `startStatusLoading()` (adds `disabled` to every `.api_button`, shows `.api_loading`) before its status check, and every return path of the checks (`getStatusOpen`, `getStatusTextgen`, `getStatusKobold`, `getStatusNovel`) ends in `resultCheckStatus()` → `stopStatusLoading()`. A failed attempt sets `no_connection` again (no event); some failures send no request (e.g. no endpoint). ST's auto-load and auto-connect start in `initRossMods` before `APP_READY` and aren't awaited. The Custom chat completion source sets "Status check bypassed" before its request
- **Chat save after a reply (E8)** (2026-11-22; `public/script.js` 1.19.1, the test install's version): the save is `saveChatConditional()` → `saveChat()` (`/api/chats/save`) or `saveGroupChat()` (`/api/chats/group/save`), always a `fetch`, always after the generation response has ended:
    - **Streamed reply, finished or Stop:** `Generate` awaits `streamingProcessor.generate()`, then, if `isFinished && !isStopped`, `onFinishStreaming()`: `MESSAGE_RECEIVED` and `CHARACTER_MESSAGE_RENDERED` (awaited, so extensions' handlers come first), then `saveChatConditional()`. Stop (`onStopStreaming()`) sets `isFinished` and aborts, so a stopped reply is saved too
    - **Not streamed, success:** `onSuccess`: `saveReply()`, then `saveChatConditional()` itself (`'/api/chats/save called by /Generate'`). Impersonate saves too (both paths: its branch only fills the input box and falls through)
    - **No save:** a stream that errors (`onErrorStreaming()` sets `isStopped`); a failed request, streamed or not (`onError`: an error answer, no model reachable, a network error, Stop of a non-streamed request); `quiet` generations (extensions' background prompts: `onSuccess` returns before saving); tool-call paths that end the generation. These always wait out the 3 s bound
    - **Auto-swipe and tool calls** start a new generation instead of saving at once (`busy` stays `true` across it); the user's message is saved at send (`sendMessageAsUser`), before the generation request
    - `saveChatConditional()` first calls `waitUntilCondition(() => !isChatSaving, 1000, 100)` (`utils.js`): a `setInterval` with **no immediate check**, so every save waits at least one 100 ms tick before its request, even when no save runs. If the 1 s timeout fires first it logs "Timeout waiting for chat to save" and **skips the save**. On a hidden page Chrome slows the interval to about once a second, so the tick and the timeout race: the save comes about 1 s late, or not at all (the reply then stays unsaved until ST's next save; the lease clears `busy` at the 3 s bound)
- **Horde is asynchronous:** `/api/horde/generate-text` only submits the job and answers its id; the reply comes from repeated `POST /api/horde/task-status` polls (`horde.js`), so `busy` covers only the submit
- **`window.name` and the URL hash** (2026-11-22; ST 1.19.1, the test install): no code in `public/` outside `public/lib` and minified libraries reads or writes `window.name`, `location.hash` or `hashchange`; neither do the test install's third-party extensions (Memory Books, TopInfoBar). The off mode's one-load fallback (E4) can use `window.name`
- **Top bar** (2026-11-22; ST 1.19.1 `public/style.css`): `--topBarBlockSize` is defined on `:root` (`calc(var(--topBarIconSize) + var(--topBarBlockPadding))`) and used by ST itself for `#sheld`'s `top`; `#top-settings-holder` has `z-index: 3005` and holds the top-bar drawers, so the protection-off banner (E9) sits at `top: var(--topBarBlockSize)` with `z-index: 3004`, under the open drawers
